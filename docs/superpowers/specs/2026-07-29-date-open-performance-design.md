# 照片图库日期打开性能设计

## 目标

优化照片图库选择日期后的加载路径，使网络图库和大日期目录能够快速显示首批内容，窗口保持可交互，快速切换日期时不会显示过期结果，也不改变现有照片分类、元数据、修图状态和总数语义。

## 当前测量与根因

测量对象为真实只读 SMB 图库 `\\Hanabe\拍照`：

- `07.27_鬼灭`：1,642 个可预览文件。目录枚举中位数约 6.6ms；逐文件读取 `Length` 中位数约 674.9ms；现有 `CreatePreviewFile` 等价路径再次读取 `FileInfo` 中位数约 685.5ms。相同网络属性被读取两遍，UI 线程仅这一项约阻塞 1.36s。
- 同一目录递归容量统计约 0.61–0.79s。
- `07.11_7.12毕业典礼`：7,465 个递归文件，容量遍历约 3.24–3.72s。

`SelectDateAsync` 目前还存在：

- 没有日期切换专用取消令牌或加载代次，旧请求可覆盖新日期。
- 在 UI 线程逐个 `ObservableCollection.Add`，并逐项触发计数和属性通知。
- 修图索引、存储元数据回写后重复执行筛选、可见项重建和缩略图工作。
- 容量递归属于次要信息，却串在日期首屏关键路径上。

因此瓶颈不是目录枚举，而是重复网络属性读取、UI 逐项通知和非首屏任务串行执行。

## 设计

### 1. 单次后台快照

新增 `LibraryDateSnapshotService`。它在后台线程对选中日期的分类目录各枚举一次，并在同一次遍历中生成不可变记录：

- 完整路径、文件名、分类和展示顺序；
- 文件长度、最后写入时间；
- 预览所需的基础类型信息。

后续 `PreviewFile` 创建和分类汇总直接使用快照中的长度，不再对同一文件重新构造 `FileInfo` 或访问 SMB 元数据。服务只读取文件系统，不打开图片像素。

### 2. 取消与加载代次

每次选择日期：

1. 取消前一个 `CancellationTokenSource`；
2. 递增加载代次；
3. 后台阶段、元数据阶段、批量上屏前均检查令牌；
4. 只有代次仍等于当前值时才允许写入 UI。

取消是协作式的；已经发出的单次文件系统调用不可强杀，但返回后不得再更新界面。

### 3. 首批优先和批量上屏

- 清除旧日期后立即显示骨架/加载状态，不让 UI 等待全部扫描结束。
- 快照生成后按稳定顺序每批 80–120 项写入界面；批次之间让出 Dispatcher。
- 集合使用批量更新机制：每批最多一次集合变更、一次总数更新和一次筛选刷新，禁止逐项重建全部可见项。
- 首批达到 100 项或快照不足 100 项时即可结束“正在打开”状态；剩余批次继续填充。
- 总项目数使用快照的最终数量，不能把“当前已上屏数量”误显示为总数。

### 4. 元数据和修图状态

- 从存储层按快照路径一次批量读取分类、评分、标签和修图状态，禁止每个文件单独查询。
- 元数据通过路径字典与快照合并，再批量更新受影响项。
- 修图索引改为图库级复用；仅当修图根目录指纹变化时重建，不因每次切换日期全量重建。
- 元数据合并完成后只执行一次最终筛选刷新；缩略图继续按可见范围懒加载。

### 5. 容量统计移出关键路径

- 日期内容首批可见后，再以低优先级后台任务计算容量。
- 容量结果使用独立取消令牌和加载代次，不能延迟照片显示，也不能把旧日期容量写到新日期。
- 对目录最后写入时间与文件数指纹未变化的日期复用容量缓存。
- 容量失败只显示“容量暂不可用”，不清空已加载照片。

### 6. 有界缓存与内存

进程内保留最近 3 个日期快照，按 LRU 淘汰。缓存保存路径和轻量元数据，不保存图片像素或完整缩略图。缓存命中仍校验目录指纹；指纹变化则后台重建。

并发限制：

- 同一时刻只有一个前台日期快照任务；
- 容量任务最多一个；
- 缩略图解码继续使用现有有界并发，不因批量上屏无限排队。

## 错误与交互

- 网络断开、目录消失或访问被拒绝时，显示具体原因并保留日历和重试入口。
- 部分分类目录失败时显示已成功分类的照片，并标记“部分内容未加载”。
- 用户连续切换日期、切换人物筛选或返回全部照片时，旧加载任务不得闪回。
- 日期组默认展开行为、人物筛选日期高亮和现有分类规则保持不变。

## 测试与验收

### 单元和集成测试

- 证明每个文件的长度只从快照读取一次，预览创建不再次访问文件系统。
- 2,000 个合成文件时验证批量通知次数有上界，而不是 2,000 次全量刷新。
- 快速选择 A、B、C 日期，最终只能显示 C。
- 在枚举、批量上屏、元数据合并和容量阶段取消均不会留下旧结果。
- 元数据、修图状态、分类总数和现有排序与优化前一致。
- 容量缓存命中、指纹失效、网络错误和部分目录失败。
- 最近 3 个日期缓存和淘汰行为。

### 性能门槛

在同一测试机和同一 SMB 网络条件下，以优化前基线对比：

- 1,500–2,000 文件日期：主线程不得出现超过 100ms 的连续日期加载工作。
- 首批照片目标在快照返回后 250ms 内上屏。
- 去除第二遍网络 `FileInfo` 后，文件属性读取耗时至少下降 40%。
- 容量统计不得计入首批可见耗时。
- 快速切换 10 次日期后仅保留 1 个前台扫描和 1 个容量任务，内存不随切换次数线性增长。

性能测试报告同时记录冷缓存和热缓存结果；不能只报告缓存命中数据。

## 非目标

- 不减少真实照片数量来换取速度。
- 不修改照片、日期目录或文件名。
- 不预先解码全部图片。
- 不引入数据库服务器、Docker、外部 API 或无限后台索引。
